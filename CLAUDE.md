# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Dough Board is a Rails 8.1 app (Ruby 3.4.8, SQLite) for tracking personal assets/liabilities. It pulls live quotes from [Finnhub](https://finnhub.io/) (via the `finnhub_ruby` gem) and scrapes stock split history from splithistory.com.

## Commands

```bash
bin/setup                       # install deps, prepare DB (first-time setup)
bin/rails server                # run the app
bin/rails db:migrate            # apply migrations
bin/rails test                  # run all tests (Minitest)
bin/rails test test/models/transaction_test.rb          # single file
bin/rails test test/models/transaction_test.rb:12       # single test by line
bin/rails test:system           # Capybara/Selenium system tests
```

```bash
bin/rails reference:exchanges   # fill the exchanges table (once, after setup)
bin/rails connections:discover  # pick up connections made on the provider's site
bin/rails connections:sync      # sync every active connection now
bin/rails plaid:sandbox         # connect a Plaid sandbox institution and sync it, no browser
bin/rails plaid:teardown        # delete every Plaid connection and release its Item
bin/rails positions:derive      # snapshot accounts fed by transactions or a loan schedule
```

`reference:exchanges` is the **only** writer of the `exchanges` table — migrations create just the two rows the pre-existing `assets.exchange` strings referred to. Run it once at setup, or assets sync with a null exchange until you do.

```bash
bin/dev                         # run web + JS watcher + CSS watcher (Procfile.dev)
```

JS is bundled separately from Ruby: `npm install` pulls esbuild (`package.json`), and `esbuild.config.mjs` bundles `app/assets/javascripts/boot.js` → `app/assets/builds/boot.js`.

## Setup

Credentials live in an **unencrypted, environment-keyed** `config/credentials.yml`
(gitignored; no `master.key`/`.enc`). Copy the template and fill in your values:

```bash
cp config/credentials.yml.sample config/credentials.yml   # then edit
```

The file is keyed by environment (`development:`, `test:`), and Rails selects the
current env's section automatically. Each section holds `secret_key_base` (generate
one with `bin/rails secret`), `finnhub.api_key`, a section per connector
(`snaptrade`, `plaid`). This override is wired up
by `ext/active_support/encrypted_configuration.rb` (patches `ActiveSupport::EncryptedConfiguration`
to read a plaintext, env-namespaced file), required early in `config/application.rb`
alongside `config.credentials.content_path = Rails.root.join("config", "credentials.yml")`.

## Architecture

**StandardAPI-driven controllers.** Controllers/routing use the `standardapi` gem, not stock Rails scaffolding. Routes are declared with `standard_resources :transactions` (see `config/routes.rb`), and `ApplicationController` includes `StandardAPI::Controller` + `StandardAPI::AccessControlList`. Controller-permitted attributes are defined in ACL modules under `app/controllers/acl/` (e.g. `TransactionACL#attributes`), **not** via `params.permit`. `ApplicationController#create` is monkey-patched to redirect on HTML requests while keeping JSON `render :show` behavior. Note: standardapi requires the `pg` gem at load time (it patches the PostgreSQL adapter) even though this app connects via sqlite3 — hence `pg` in the Gemfile.

**External data via singletons.** Two service objects use the `Singleton` + `method_missing` class-delegation pattern so they're called as `Finnhub.quote(sym)` / `SplitHistoryScraper.splits(sym)`:
- `config/initializers/finnhub.rb` — thin wrapper over the `finnhub_ruby` gem's `DefaultApi#quote` (a hand-written client whose `quote` returns a Hash); `Finnhub.quote(sym)` returns the current price (the `c` field), or `nil` when Finnhub has no data (an unknown symbol returns `c=0`) or the request fails (e.g. rate limited, raising `FinnhubRuby::FinnhubAPIException`). Finnhub only prices crypto for exchange-prefixed pairs, so `Asset#quote_symbol` maps crypto symbols to `BINANCE:<SYM>USDT` (stocks/funds pass through unchanged); `Quote#fetch` requests `asset.quote_symbol`.
- `config/initializers/split_history_scraper.rb` — Nokogiri HTML scraper returning `[split_date, ratio]` pairs.

**Connectors** (`app/lib/connectors/`) use the same Singleton + delegation pattern, but as a class hierarchy — `Connectors::Base` declares what any service must answer (`accounts`, `positions`, `cash`, `transactions`, `authorizations`, `exchanges`), and everything above deals in plain hashes so no SDK object or provider field name escapes a subclass. `Connectors.for("snaptrade")` resolves through `Connectors::REGISTRY`. Note `Base.method_missing` takes `**kwargs` — without it Ruby 3 folds a call's keywords into a positional Hash and `transactions(connection, account, since:)` arrives as three positional arguments. (The two initializer singletons above have the same gap; they just never pass keywords.)

**One instrument, one symbol.** A venue's private spelling is translated at the connector boundary by `Base#canonical_symbol`, off the flat `Base::SYMBOL_ALIASES` map — Kraken files its older listings under ISO-4217-style codes (crypto prefixed `X`, fiat prefixed `Z`, Bitcoin as `XBT`), so the coin Coinbase reports as `BTC` arrives as `XXBT`. Left alone it becomes a second `Asset` with its own tile and cost basis and no price at all, because `Asset#quote_symbol` goes on to ask Finnhub for `BINANCE:XXBTUSDT`. The map is keyed by symbol rather than by venue (none of these codes is a real ticker elsewhere, and activity rows don't reliably say which venue they came from) and lists only the prefixed listings — Kraken leaves newer coins alone, so stripping an `X` by rule would mangle `XTZ`. Both connectors call it on every symbol they emit. Adding an entry only fixes future syncs; assets already filed under the old spelling are folded by a migration (`20260823120000`, the pattern to copy — it merges positions rather than repointing them, since `(account, asset, as_of)` is unique).

**There are two ways a connection gets made**, and a connector declares which it supports — `discoverable?` (the default) or `linkable?`. A *discoverable* service can be asked what its credentials are already connected to, because the connecting happened on the service's own site (SnapTrade); `Connection.discover!` creates a row per authorization. A *linkable* service issues a secret per connection and only through a browser flow we run ourselves (Plaid Link), so `Connection.link!` trades that flow's one-time token for credentials stored on `connections.credentials` — which is what that column has always been for. `Connectors.discoverable`/`.linkable` drive the connections page's buttons, and both filter through `configured?` so a connector with no credentials isn't offered at all. `Base#disconnect!` releases the provider's side when a connection is deleted (a `before_destroy`), because Plaid caps a plan by Items and a deleted row would otherwise leave the slot spent.
- `Connectors::SnapTrade` wraps the official `snaptrade` gem. It authenticates with a **Personal API key** — one person's own connections — which means no user registration and no in-app connection portal: connections are made on SnapTrade's site and picked up by `bin/rails connections:discover`. The gem was written for SnapTrade's Commercial flow and makes `user_id`/`user_secret` required keyword arguments on every account call; a Personal key has no such user and the API ignores both, so the connector passes blanks.
- Live position payloads do **not** match SnapTrade's published docs: a position is `{units, price, cost_basis, currency, instrument}`, where `instrument` is one of `StockInstrument`/`EtfInstrument`/`MutualFundInstrument`/`CryptoInstrument`/`AdrInstrument`/`OtherInstrument` carrying `symbol`, `kind`, `description`, `figi_instrument`, and an `exchange` that is a **plain MIC string** (`"XNAS"`). Two traps: SnapTrade's `cost_basis` is the cost of *one unit* (so it maps to `Position#average_price`, and `Position#cost_basis` — the total — is derived from it), and `Exchange` must be matched on `mic_code` **then** `code`, because crypto venues come back as `COIN`/`KRAK` with a null `mic_code`.
- `Connectors::Plaid` wraps the official `plaid` gem and is the linkable one. Every `::Plaid` in it is deliberately root-scoped — inside `Connectors::Plaid` a bare `Plaid::` resolves to itself. `plaid.environment` in the credentials file picks sandbox or production, and each has its **own secret**; `Connectors::Plaid.environment` is what `bin/rails plaid:sandbox` guards on.
- One Plaid connection is one **Item** (one institution), and `/accounts/get` returns every account behind it — bank, brokerage, card and loan — so a single Item covers all of them. `SYNCED_ACCOUNT_TYPES` keeps `investment`/`brokerage`/`depository` plus the `DEBT_ACCOUNT_TYPES` (`credit`/`loan`); only what Plaid can't classify is dropped. A bank account's cash comes from `balances.current` via `#cash`; a brokerage's comes through `#positions` as a holding in a security of type `"cash"` — counting both would double the account.
- **Debts are positions with negative units**, not a model of their own. A card or a loan holds nothing — its balance *is* the position — so `#positions` returns one row of dollars at $1.00 against an `Asset` of type `liability`, and the snapshot, pruning, account total and portfolio all work on it unchanged. Two traps: Plaid signs a debt from the lender's side (a positive `current` is what's *owed*, a negative one an overpaid card), so the connector negates it; and the asset is the **kind** of debt (`DEBT:CREDIT_CARD`, `DEBT:HOME_LOAN`, …, mapped from `account.subtype` by `DEBTS_BY_SUBTYPE`), so every card folds into one portfolio line while each account keeps its own row. The `DEBT:` prefix matters — `LOAN` and `AUTO` are real tickers. Debt accounts skip `/investments/*` entirely: their activity is the `transactions` product, which this connector doesn't ask for. Because `#positions`, `#cash` and `#transactions` all now ask what kind of account they're looking at, `#accounts_get` holds its answer per access token for `ACCOUNTS_TTL` (1 minute) — it answers for the whole Item at once, ConnectionJob asks per account, and Plaid rate-limits per Item.
- **Some brokerages report only what an account is worth**, and that balance is then the whole holding. Titan (cleared by Apex) answers `/investments/holdings` with no holdings for its accounts and has no investments activity either, so an account that syncs off holdings alone comes out empty and the portfolio silently loses all of it. `#positions` therefore falls back to `#balance_positions` when a brokerage account maps to **zero** holdings — the same shape as a debt in the other direction: one row of dollars at $1.00 against an `Asset` of type `balance` (`Asset#face_value?`, so it is never quoted and `cached_price` is 1.0). Holdings always win when there are any, so nothing is counted twice, and the day the institution starts reporting them the balance row is pruned like any holding that went away. Two deliberate choices: the asset is **not** the `USD` cash asset (the money is invested, not uninvested, and folding it in would overstate what's liquid), and unlike a debt it is **per account** rather than per kind — `FUND:<INSTITUTION>-<ACCOUNT NAME>`, because an account named "Individual" is named that at every brokerage there is. Only `investment`/`brokerage` accounts take this path: a `depository` balance is already reported by `#cash`, and a balance row too would double it. The same institutions refuse `/investments/transactions`, so `#transactions` swallows `NO_HOLDINGS_ERRORS` there as well rather than stranding the whole connection over an account with nothing to browse.
- **Linking is per kind, because products can't simply be added together.** Link shows only institutions that support *every* product in `products`, and hardly any support both `investments` and `liabilities` — the sandbox's own investments institution refuses `liabilities` outright. So `Connectors::Base::LINK_KINDS` (`holdings` = bank or brokerage, `debts` = card or loan) picks the one required product and `#link_token` passes the rest as `required_if_supported_products`, which is taken wherever the chosen institution happens to support it. The connections page renders one Connect button per kind. Update mode still names no products at all: a reconnect signs back in to what's already linked, and an Item that needs the other product is linked again as a second connection. `plaid:sandbox` has no Link to negotiate for it, so `#sandbox_public_token` asks `/institutions/get_by_id` what the test institution supports and mints against the intersection — `bin/rails plaid:sandbox[ins_109508]` is the liabilities-side run.
- Plaid traps worth knowing, all confirmed against the live sandbox: `holding.cost_basis` is the **total** for the whole holding (the opposite of SnapTrade's per-unit one), so `average_price` is that over `quantity`. `security.is_cash_equivalent` is **true for Bitcoin**, so cash is identified by `security.type == "cash"`, never by that flag. Investment transactions sign `quantity` by direction (a sale is negative) but `Transaction::UNIT_SIGNS` applies the direction itself, so the connector passes `quantity.abs` — except for `transfer`, which is reported both ways under the one type and carries its direction in the sign. `investment_transaction.subtype` is the precise field (`type` only says buy/sell/cash/fee/transfer/cancel), so `TYPES_BY_SUBTYPE` is matched first and `TYPES_BY_TYPE` is the fallback; `cancel` is in neither, because it reverses an earlier transaction rather than being one.
- A security often has **no ticker** (mutual funds, treasuries). Dropping those would silently understate the portfolio, so the symbol falls back `ticker_symbol → cusip → isin → "PLAID:<security_id>"`. Nothing quotes a `PLAID:` symbol, so `Position.portfolio` values it at the price Plaid reported.
- **`plaid:sandbox` is how this gets exercised.** Plaid's sandbox mints an Item without a browser, so the whole path — exchange, accounts, holdings, activity, pruning — runs against the real API for free and without spending one of the production Items a plan is capped by. `plaid:teardown` releases them again. `Connection#needs_reauthorization?` reads Plaid's `ITEM_LOGIN_REQUIRED` off `last_error` (`Connectors::ConnectionError#code` carries the provider's own code) and the connections page then offers Reconnect, which opens Link in **update mode** — that flow returns no new token, because the credentials already stored start working again.

**Model layer does the fetching automatically.** The `type` column on `Asset` and `Transaction` is a plain string, not Rails STI — both models set `self.inheritance_column = nil` to disable STI while keeping a `type` attribute (`Asset` type ∈ stock/fund/crypto/cash/liability/balance/real_estate/vehicle, `Transaction` type ∈ `Transaction::TYPES` — the brokerage activity vocabulary, `buy`/`sale`/`dividend`/`fee`/…).
- `Quote` has a `before_validation :fetch` that lazily populates `price`/`quoted_at` from **the asset's valuator** (see below). When the source returns no price (unknown symbol, rate limit, a listing that no longer parses), `fetch` does `throw :abort` so the blank Quote is **not** persisted. `Asset#current_quote` returns a cached quote if one is still current, otherwise **creates a new Quote** (triggering a fetch). Reading `asset.price` can therefore hit the network — except for a slow valuator, which is queued instead.
- `Asset#load_splits` caches scraped splits for 24h via the `splits_updated_at` timestamp. It is called from `LoadSplitsJob`, not from a request: saving a transaction never blocks on the scraper.
- `Transaction` auto-creates its `Asset` from a virtual `symbol` accessor (`before_validation :create_asset`) and computes `adjusted_quantity` (`before_save`) by multiplying `quantity` through every split **already on hand** that occurred after `executed_at`. `after_create_commit` then enqueues `LoadSplitsJob` (skipped while `splits_updated_at` is <24h old, so an import of many rows for one symbol queues one job), which rescrapes and force-recomputes `adjusted_quantity` for every transaction against that asset. A transaction is therefore briefly unadjusted between save and job completion. `adjusted_quantity` no longer feeds the portfolio directly — it feeds `Transaction#units`, which `DerivePositionsJob` folds into positions.
- Editing an `Asset` invalidates what its identity implies: `after_update` clears cached `quotes` when `symbol` or `type` changes (both feed `quote_symbol`), and on a `symbol` change also drops `splits` and enqueues `LoadSplitsJob`.
- **Jobs run on Sidekiq in production only** (`config/environments/production.rb` sets `config.active_job.queue_adapter = :sidekiq`); development and test stay on the default in-process adapters so neither needs a Redis. Sidekiq connects to `REDIS_URL`, falling back to `redis://localhost:6379/0`, and reads `config/sidekiq.yml`. **Two queues, weighted 4:1** — `default` for anything a person is waiting on (`ConnectionJob`, `DerivePositionsJob`) and `scrapes` for `LoadSplitsJob`, which fetches splithistory.com one asset at a time and arrives in the thousands after a sync. Weighted rather than strictly ordered so the scrapes still progress without ever being the only thing a worker looks at. `config/sidekiq.yml` must name every queue a job uses or that job is enqueued and never runs — `test/jobs/queues_test.rb` pins that. The worker unit must not pass `-q` or `-C`, or this file stops applying (see `BUILD.md` §7; a stray `-q '*'` once had a worker polling a queue literally named `*` while thousands of jobs sat untouched). Workers are instances of a systemd template unit — `dough-board-worker@0.service`, `@1`, … — restarted after every deploy by `worker:restart` (`lib/capistrano/tasks/worker.rake`); set `:worker_instances` in `config/deploy.rb` if the server enables more than instance 0.
- **Sidekiq's dashboard is mounted at `/jobs`.** It's a Rack app, so it bypasses `ApplicationController` entirely and never runs `before_action :require_login` — `LoggedInConstraint` (`app/lib/logged_in_constraint.rb`) is what stands in, reading the same `session[:logged_in]` the rest of the app sets. The constraint is referenced through a lambda in `config/routes.rb` so the constant resolves per request rather than at draw time, keeping it reloadable in development. A rejected constraint would otherwise fall through to a bare 404, so a catch-all beneath the mount redirects to the login form instead. Rendering the dashboard needs a live Redis, which development and test don't run.

**Valuators** (`app/lib/valuators/`) are to prices what connectors are to accounts, and use the same Singleton + class-delegation pattern: `Valuators::Base` declares `price(asset)` — a Float, or nil when this source has nothing to say — and `Valuators.for("depreciation")` resolves through `Valuators::REGISTRY`. `Quote#fetch` asks `asset.valuator`, so nothing above the layer knows a house from a share. Which one an asset uses is `assets.valuation_source`, and null means *whatever its type implies* (`Asset::VALUATORS_BY_TYPE`: real_estate → manual, vehicle → depreciation, everything else → finnhub), so every pre-existing row keeps going to Finnhub without being rewritten. Whatever a source needs to do its job — a purchase price and date — lives on the `assets.valuation_key` json column; the valuator declares those fields through `#keys`, which is both what the asset form renders and (via `Valuators.key_names`) what `AssetACL` permits, because permitting a json column wholesale would let a form post write arbitrary JSON onto an asset.
- **Two timings, and they are not the same number.** `#quote_ttl` is how long an answer stands as the current price (`Asset#cached_quote`); `#refresh_interval` is how often `quotes:refresh_all` asks again (`Asset#quote_due?`). Finnhub is 24h/every run — the original behaviour, a cache of something that moves by the minute. The other two **never expire** and are asked daily or never: a value that only changes when someone changes it is the best number anyone has, so letting it go stale would blank the holding out rather than improve it, and the half-hourly schedule would otherwise write a quote per run for a number that hadn't moved.
- **Real estate has no automatic source, and that was a finding, not an omission.** There is no cheap way to buy a Zestimate — Zillow's own feed is Bridge Interactive, which wants an MLS affiliation and ~$500/mo — and the listing page is behind PerimeterX, which fingerprints TLS: a Ruby HTTP client is refused with a 403 captcha page from a datacenter *and* a home address, with or without a full Chrome header set, and the login page an authenticated fetch would need is the same wall. A scraper was written, tested against a live listing, and removed. So a house is `manual`.
- `Valuators::Depreciation` prices a car by modelling the curve instead of looking it up: Kelley Blue Book has no self-serve API and its number is behind a mileage-and-condition form rather than a page that can be read. Value decays at `annual_rate` percent a year (default 15) from `purchase_price`, floored at `residual_value` (default 10% of what was paid) — an exponential decay left alone approaches zero, and an old car is not worth nothing. It costs nothing, can't be rate-limited and can't break.
- `Valuators::Manual` never fetches: the value is whatever was last typed into the asset form's **Record a value** field, which writes a `Quote` like any other source, so an override ages and renders like every other price rather than being a second kind of price. It's what real estate resolves to, the fallback for anything else nothing can price (a boat, a painting, a stake in a private company), and the escape hatch for any source that stops working. `Asset#entered_value` is the virtual attribute behind it, recorded in an `after_save`.
- A house and a car are held exactly like a share — one position, some number of units, a price each — so the treemap, account totals and value history need no changes. Their symbols are namespaced (`PROPERTY:12-OAK-ST`, `VEHICLE:2019-OUTBACK`) for the same reason Plaid's debts are: `HOME` and `AUTO` are real tickers. `Asset#splittable?` keeps them away from splithistory.com, which would happily be asked about `PROPERTY:12-OAK-ST`. Assets have `new`/`create` routes for exactly this — everything else gets created by a transaction's symbol or by a sync, and a house has neither.

**Portfolio aggregation reads `Position`, not `Transaction`.** A `Position` is one holding as of a moment: `(account, asset, as_of)` is unique, and every row written by a single run shares that run's `as_of`, with the account recording the newest in `accounts.positions_as_of`. That pair is what makes "the current snapshot" a plain equality check (`Position.current`) instead of a window function SQLite would have to emulate, and it's what gives portfolio value over time for free.

- `Position.portfolio` folds any scope into `[{symbol:, asset:, units:, price:, value:}, ...]`. It's a relation-level method, so `Position.current.portfolio` is the whole portfolio and `account.current_positions.portfolio` is one account's. It prices holdings off `asset.cached_price` (falling back to the broker's `position.price`) so the value rendered matches what the page's JS recomputes when it refreshes quotes. It drops holdings whose units are **zero**, not negative — a debt is a negative holding, so the sum of a portfolio is a net worth. A treemap has no area for one, so `_portfolio.html.erb` and `accounts/_treemap.html.erb` say what's owed in words above tiles that stay the assets.
- `AssetsController#index` (the root route) and `Account#portfolio`/`#value` both go through it.
- **`accounts.positions_source` says who writes an account's positions**, and there is no partial ownership — `DerivePositionsJob` rewrites and prunes a whole snapshot, so it either owns an account or doesn't touch it. `transactions` (the default) means the job folds them from the account's own transactions; `manual` means the positions are the record of truth and nothing rewrites them; `amortized` means `AmortizeLoanJob` works the balance out from the loan's terms; `connection` means `ConnectionJob` syncs them from the institution. `Account#derives_positions?` is the guard, checked at the top of `DerivePositionsJob`, in `Transaction#derive_account_positions`, and in the `positions:derive` task. Only a `manual` account's positions are editable in the UI (`Position#editable?`), and the position form's account select lists only those accounts. `connection` is not a choice anyone makes — a connector sets it on the accounts it creates, so the account form shows it as text (`Account::SELECTABLE_POSITIONS_SOURCES` is what the select offers).
- **`ConnectionJob`** mirrors `DerivePositionsJob`'s snapshot contract exactly: no `as_of` corrects the current snapshot in place, an `as_of` (from `connections:sync`, hourly at `:10`) appends a history point, and holdings the institution stops reporting are pruned. Failures are recorded on `connections.last_error` for the UI **and** re-raised so the queue records a failure rather than a quiet no-op. Uninvested cash rides along as a position against the `USD` cash asset. A synced account's transactions are upserted too, deduped on the existing `(account_id, foreign_id)` index — they're history to browse, not the source of its holdings.
- **A synced account's name is the one thing a person can own.** Everything else on the account row is overwritten every sync, but `accounts.foreign_name` records what the institution last called it, and `Account#name_from_institution` only takes their name while `name` still equals `foreign_name`. So an untouched account follows a rename on their side, and a hand-typed name survives every later sync (`Account#renamed?` is what the account form explains). Naming it after the institution's own name is therefore not a rename — a name has to differ to be an override.
- **A loan is an account whose one holding is calculated, not recorded** (`positions_source: "amortized"`). `accounts.loan_terms` holds the principal, annual rate, term in months, start date and kind of debt; `Amortization` (`app/lib/amortization.rb`) is the value object that turns them into a payment and a balance, and `AmortizeLoanJob` writes that balance as a position. Nothing about a mortgage is worth fetching — the balance follows from the terms — which makes it the debt-side sibling of `Valuators::Depreciation` above, with one structural difference worth holding onto: a debt's number is a **quantity**, not a price (dollars owed at $1.00 each), so it is written as position units rather than as a quote, and it belongs to whoever owns the account's snapshot rather than to the pricing layer. It mirrors `DerivePositionsJob`'s snapshot contract exactly: no `as_of` corrects the current snapshot in place, an `as_of` appends a history point, everything else in the snapshot is pruned. Because `Amortization#balance` takes a date, the history it leaves is a real paydown curve rather than a series of guesses.
  - The position is **negative units of dollars at $1.00** against a `DEBT:*` asset, which is the shape `Connectors::Plaid` already writes — so a mortgage kept by hand and one synced from a lender fold into one portfolio line instead of two. That shared vocabulary is why `DEBT_NAMES` moved from inside the Plaid connector to `Asset::DEBT_NAMES`.
  - `Amortization.from` returns **nil** for terms that don't describe a loan, and the job writes nothing when it does. Writing a zero instead would read as a mortgage that had been paid off, which is why `Account` also validates the terms rather than letting a half-filled-in account save.
  - Two traps worth knowing: the rate is entered as a percentage (`6.25`, not `0.0625`), and `#balance` returns exactly `0` once the term is complete — a lender rounds the level payment to the cent and adjusts the final one, and without that rule the rounding leaves a dollar or two owed forever. It is also a *calculation*, not a statement: an extra payment or an escrow change won't appear, which the account page says out loud.
- Switching an account `transactions` → `manual` **keeps whatever was last derived**, so the holdings already worked out become the starting point for hand maintenance rather than being thrown away. Switching back hands the snapshot to the job again, which rewrites it wholesale on its next run.
- The fold uses `Transaction::UNIT_SIGNS` — a type absent from that table (a dividend, a fee) moves cash, not shares, and must not change the unit count. With no `as_of` the job **corrects the account's current snapshot in place**; the `positions:derive` rake task passes one to append a history point. A transaction's `after_commit` enqueues a run, which `Transaction.without_position_derivation` suppresses for bulk paths like the CSV import (which enqueues one run at the end instead).
- Cash is carried as a position against an `Asset` of type `cash`, worth face value — `Asset#price`/`#cached_price` return `1.0` for it and `Quote#fetch` aborts, so it never reaches Finnhub. Type `liability` is the same thing owed rather than held; `Asset#face_value?` is what both go through, and the asset form offers `liability` (but not `cash`) so a loan no connection reaches can be kept by hand. Type `balance` is the third one through that gate — a whole account whose institution reports only its value, dollars held at $1.00 apiece (see the Plaid connector above); nothing but a connector creates one, so the form doesn't offer it either.

**Demo mode** (`app/lib/demo_mode.rb`) shows the app to somebody without showing them what's in it: every holding renders as a random **5–20%** of what's really held. Prices are public and stay real — it's the *quantity* that's scaled, which matters because `boot.js` recomputes each value as `data-quantity × price` when fresh quotes land, so a doctored value alone would be corrected back to the truth a second after the page loaded.
- **The factor is derived, not drawn**: `SHA256(seed:symbol)` folded into the band. A random number per render would give the same holding a different size on every page, and the row, the account total and the portfolio total would each disagree; this way one asset has one factor everywhere, for as long as the seed stands. Each asset gets its *own* factor, so proportions between holdings move too — one number read off a screenshot says nothing about any other. `DEMO_SEED` re-rolls them all; the default seed is `secret_key_base`, and is never rendered.
- **It is a display layer and nothing else.** `Current.demo` is set from the session by `ApplicationController`, so it is on only inside a request that asked for it — `DerivePositionsJob`, `ConnectionJob` and `AmortizeLoanJob` never see it and always write the real figures. `DemoMode.scale` returns its argument untouched when the demo is off, so call sites don't branch. It's applied in `Position.portfolio` (which is what the portfolio page, the treemaps and `Account#value` all read), in `positions/_table.html.erb` (units, value, cost basis), and in `accounts/_loan.html.erb` — a real mortgage's terms next to a scaled balance would give away both, so the loan's dollar figures take the same factor as its `DEBT:` asset and its rate, dates and payment count stay as they are.
- Turned on for one browser by the header's **Demo** button (`POST /demo`, `DemoController`), or for a whole deployment by setting `DEMO_MODE` — in which case there's nothing to switch off and the header shows a label instead of a toggle. Transaction quantities are **not** scaled: they're the activity behind a holding rather than the holding, and a demo that hides one but not the other is worth knowing about before showing the Activity tab.

**Assets** use the modern Rails pipeline: Propshaft serves fingerprinted assets from `app/assets/builds`, `jsbundling-rails` drives esbuild for JS (`esbuild.config.mjs`), and `tailwindcss-rails` compiles `app/assets/tailwind/application.css` → `app/assets/builds/tailwind.css` (Tailwind v4). Both build steps run automatically on `bin/rails test`/`assets:precompile`; use `bin/dev` (`Procfile.dev`) to watch them in development. The former Condenser/SassC/`uniform-ui` stack is gone — the layout links `tailwind.css` and the bundled `boot.js`, and the old uniform `Tooltip` is now a small vanilla `data-tooltip` handler in `boot.js`.
